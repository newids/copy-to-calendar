# 일정 캡처 앱 기획서

Oct 19, 2026 · @JS Choi

## 1. 개요

**한 줄 정의:** 카톡·문자·디스코드·슬랙·메일로 받은 일정 문구를 붙여 넣으면, LLM이 날짜·시간·장소·참석자를 추출해 Google Calendar 또는 Apple Calendar에 한 번의 확인으로 등록해 주는 앱. macOS / Windows / iOS / Android 4개 플랫폼을 단일 코드베이스로 동시 출시한다.

**서비스명:** AI Copy To Calendar (약칭·코드명 `C2C`, 구 가칭 PasteCal). 아이콘 방향은 미결 사항 참조.

**해결하는 문제**

- 일정 통보의 80% 이상이 캘린더 초대가 아니라 자연어 메시지("담주 목욜 7시 강남에서 봐요")로 온다. 사용자는 메시지를 읽고 → 캘린더 앱을 열고 → 날짜를 찾아 → 제목·장소를 다시 타이핑하는 4단계를 매번 반복한다.
- 한국어 메시지는 상대 날짜("담주", "모레", "이번 주 금"), 축약 시간("저녁 7시", "점심"), 음력·명절 표현이 섞여 있어 기존 규칙 기반 날짜 인식(iOS 데이터 감지기 등)이 자주 틀린다.
- 메시지 앱별로 캘린더 연동 UX가 제각각이고, 데스크톱에서는 그마저도 없다.

**핵심 가치**

1. 복사 → 붙여넣기 → 확인, 3초 안에 등록 완료
2. 한국어 자연어 일정 인식 정확도 95% 이상 (내부 평가셋 기준)
3. 어떤 플랫폼에서 복사했든 같은 경험, 같은 캘린더

## 2. 목표와 범위

**목표:** 출시 6개월 내 MAU 5만, 붙여넣기→등록 전환율 70%, 등록 후 24시간 내 수정 비율 10% 이하.

**성공 지표**

| 지표 | 목표 | 측정 방법 |
| --- | --- | --- |
| 파싱 정확도 (날짜·시간) | 95% 이상 | 한국어 메시지 500건 평가셋, 주 1회 자동 회귀 |
| 붙여넣기 → 등록 전환율 | 70% 이상 | 클라이언트 이벤트 로그 |
| 등록까지 소요 시간 (중앙값) | 5초 이하 | 붙여넣기 시점 → 등록 완료 시점 |
| 등록 후 사용자 수정률 | 10% 이하 | 등록 직후 수정 이벤트 |
| 플랫폼별 크래시 프리 세션 | 99.5% 이상 | 크래시 리포팅 |

**MVP 범위 (v1.0)**

- 텍스트 붙여넣기 입력 (클립보드 / 공유 시트 / 수동 입력)
- LLM 기반 일정 추출: 제목, 시작·종료 일시, 장소, 참석자, 메모, 반복 여부
- 추출 결과 확인·수정 카드 (한 화면)
- Google Calendar, Apple Calendar(EventKit) 등록
- 한국어·영어 지원
- 4개 플랫폼 동시 출시

**제외 범위 (v1.0에서 하지 않음)**

- 메시지 앱에 직접 접근해 자동 수집 (카카오톡 API 미공개, 프라이버시 리스크)
- 이미지·스크린샷 OCR (v1.5 후보)
- Outlook / Naver 캘린더 (v1.5 후보)
- 일정 자동 등록 (사용자 확인 없는 등록은 하지 않음)
- 공유 캘린더 협업, 팀 기능

## 4. 핵심 기능 정의

| --- | --- | --- |

### 4.2 AI 분석

- 추출 항목: 제목, 시작 일시, 종료 일시, 종일 여부, 장소, 참석자, 메모(원문), 반복 규칙, 알림 제안
- 모호성 플래그: 연도 누락, 오전/오후 불명, 기간 불명, 날짜 후보 복수 — 각 항목에 신뢰도와 대안 값을 함께 반환
- 기본값 규칙: 종료 시간 없으면 +1시간, "새벽"=05:00, "아침"=08:00, "오전" 단독이면 10:00, "점심"=12:00, "오후" 단독이면 13:00, "저녁"=19:00, "밤"=19:00 (모두 설정에서 변경 가능, 새벽·아침·오후·밤은 2026-10-22 결정). 근무시간 기본 09:00~18:00 (설정에서 변경 가능, 2026-10-27 결정)
- 컨텍스트: 사용자 시간대, 현재 날짜, 설정된 근무 시간, 최근 등록한 장소 목록을 프롬프트에 포함

### 4.3 검토·수정 카드

- 한 화면에 제목 / 일시 / 장소 / 참석자 / 캘린더 선택 / 알림을 모두 표시, 각 필드 탭으로 인라인 수정
- 모호한 필드는 노란 테두리 + "다른 해석: 10/30(금)" 형태의 원탭 대안 칩
- 원문은 접힌 상태로 하단에 보존, 등록 시 이벤트 메모에 포함(옵션)
- 같은 시간대에 기존 일정이 있으면 충돌 경고

### 4.4 캘린더 등록

- 대상 캘린더: Google Calendar (계정별 다중 캘린더 선택), Apple Calendar (iOS/macOS EventKit, iCloud·Exchange·로컬 캘린더 모두)
- 기본 캘린더 1개 지정, 카드에서 매번 변경 가능
- 등록 직후 "실행 취소" 5초 토스트, 같은 토스트에 **"답장 복사"** 버튼 — "네, 10/24(토) 10시 3층 강당 참석하겠습니다"처럼 추출값으로 채운 템플릿 문구를 클립보드에 넣어 메시지 앱으로 돌아가 바로 답할 수 있게 한다 (LLM 불필요, v1.0 포함)
- 중복 감지: 같은 제목 + 같은 시작 시각(±15분) 이벤트가 이미 있으면 "이미 있는 일정입니다 — 업데이트 / 새로 등록 / 취소"

### 4.5 부가 기능 (v1.0 포함)

- 최근 등록 히스토리 (원문 + 결과, 30일, 로컬 보관)
- 온보딩: 캘린더 연결 → 기본값 설정 → 샘플 메시지로 첫 등록 체험
- 설정: 기본 캘린더, 기본 시간값, 알림 기본값, LLM 공급자 선택(클라우드 / 온디바이스), 단축키

## 5. AI 파싱 설계

파싱은 "LLM 1회 호출 + 결정적 후처리" 2단계로 구성한다. LLM은 의미 해석만 맡고, 날짜 산술·시간대 변환·검증은 코드가 맡는다.

### 5.1 추출 스키마 (LLM 출력, JSON)

원문에 연도까지 적힌 절대 날짜("2026.10.24(토) 오전 10시~12시 학부모 설명회, 3층 강당")는 `explicit`에 넣는다:

```json
{
  "events": [
    {
      "title": "학부모 설명회",
      "start": {
        "explicit": {"date": "2026-10-24", "time": "10:00"},
        "relative": null,
        "confidence": 0.95
      },
      "end": {
        "explicit": {"date": "2026-10-24", "time": "12:00"},
        "relative": null,
        "confidence": 0.95
      },
      "all_day": false,
      "location": "3층 강당",
      "attendees": [],
      "recurrence": null,
      "notes": "원문 발췌",
      "ambiguities": []
    }
  ],
  "no_event_found": false
}
```

"담주 목욜 저녁 7시"처럼 원문에 절대 날짜가 없으면 `explicit`은 null, `relative`에 중간 표현을 넣는다:

```json
"start": {
  "explicit": null,
  "relative": {"week_offset": 1, "weekday": 4, "time_word": "저녁", "hour": 7},
  "confidence": 0.9
}
```

"10/24(토)"처럼 연도가 없으면 `explicit`은 null, `relative`에 월·일만 넣는다. 연도는 코드가 5.3 규칙으로 정하고, `year_missing` 플래그와 대안 값도 코드가 세운다 (2026-10-22 결정, ADR 0001):

```json
"start": {
  "explicit": null,
  "relative": {"month": 10, "day": 24, "time_word": "오전", "hour": 10},
  "confidence": 0.95
}
```

"이번 주 금요일 or 다음 주 화요일"처럼 후보가 여럿이면 후보마다 이벤트를 따로 내고, 같은 `candidate_group` 번호로 묶는다. 일정 두 개인지 후보 두 개인지 모델이 확신하지 못해도 이벤트를 따로 내면 되고, 둘 다 카드로 보여 준 뒤 사용자가 등록할 것을 고른다 (5.4, 2026-10-22 결정):

```json
"events": [
  {"title": null, "start": {"explicit": null, "relative": {"week_offset": 0, "weekday": 5}, "confidence": 0.6}, "candidate_group": 1},
  {"title": null, "start": {"explicit": null, "relative": {"week_offset": 1, "weekday": 2}, "confidence": 0.6}, "candidate_group": 1}
]
```

- 스키마는 클라우드·로컬 공통 하나다. 모델은 `explicit`(원문에 연도까지 적힌 절대 날짜가 있을 때)과 `relative`(상대 표현일 때) 중 하나를 채우고, 날짜 확정은 항상 코드(5.3)가 한다 — 클라우드 소형 모델도 월말·윤년 경계에서 틀리므로 모델이 계산한 날짜를 그대로 믿지 않는다
- `explicit`과 `relative`가 둘 다 있으면 코드가 둘을 계산해 비교하고, 다르면 모호성 플래그를 세운다
- 날짜·시간은 ISO 8601 로컬 표기, 시간대는 코드에서 사용자 설정값을 붙인다
- `recurrence`는 RFC 5545 RRULE 문자열 (`FREQ=WEEKLY;BYDAY=MO`)
- `ambiguities`가 비어 있지 않으면 카드에서 해당 필드를 하이라이트
- 구조화 출력(JSON mode / tool use)으로 강제하고, 파싱 실패 시 1회 재시도 후 수동 입력 폴백

### 5.2 프롬프트 전략

- 시스템 프롬프트에 넣는 컨텍스트: 현재 일시(요일 포함), 사용자 시간대, 근무시간, 기본 시간값(점심·저녁), 최근 사용 장소 10개
- 한국어 상대 표현 사전을 프롬프트에 명시: 담주/다담주, 모레/글피, 이번 주 vs 다음 주 경계(월요일 시작, ISO-8601 기준 — 5.3 표와 동일), 월말/월초, 상순/중순/하순
- 메시지 메타데이터(수신 시각)가 있으면 "오늘"의 기준으로 사용 — 사용자가 3일 전 메시지를 붙여 넣는 경우 대비. 없으면 붙여넣기 시점 기준이며 카드에 "기준일: 10/19" 표시
- 예시 10개 내외의 few-shot (공지문, 단톡 대화, 영문 메일 초대, 복수 일정, 일정 없음)
- 출력 언어: 제목은 원문 언어 유지, 추출하지 않은 정보는 절대 지어내지 않음 (null)

### 5.3 한국어 상대 날짜 처리 규칙 (후처리 코드)

### 5.4 모호성 해결 UX

1. 신뢰도 0.8 이상 → 그대로 표시
2. 0.5\~0.8 → 필드 하이라이트 + 대안 칩 1\~2개
3. 0.5 미만 또는 복수 후보 → 카드 상단에 "어느 날짜인가요?" 선택 UI, 선택 전 등록 버튼 비활성. 복수 후보(`candidate_group`)는 후보마다 카드를 보여 주고 사용자가 등록할 것을 하나 이상 고른다 — 후보인지 별개 일정인지 사용자가 판단한다
4. 일정 없음 → "일정을 찾지 못했어요. 직접 입력할까요?"

### 5.6 로컬 LLM 지원 (Ollama, LM Studio 등)

사용자가 이미 돌리고 있는 로컬 LLM 서버를 그대로 쓰게 한다. 앱이 모델을 내장하지 않으므로 용량·라이선스 부담이 없고, 프록시를 거치지 않아 비용도 0이다.

**연결 방식 (설정 > AI 모델 > 로컬 서버)**

- 프리셋: Ollama (`http://localhost:11434`), LM Studio (`http://localhost:1234/v1`), 직접 입력 (OpenAI 호환 URL + 선택 API 키)
- 모델 목록은 서버의 `/v1/models` (Ollama는 `/api/tags`)를 조회해 드롭다운으로 표시
- "연결 테스트" 버튼: 샘플 메시지 1건을 보내 응답 시간과 JSON 유효성을 표시
- "내 모델 정확도 측정": 내장 평가셋 50건을 돌려 날짜·시간 정확도를 백분율로 보여 준다 — 사용자가 모델을 고르는 근거가 된다
- 모바일에서는 같은 설정으로 LAN 또는 Tailscale 주소의 데스크톱 서버를 가리킬 수 있다 (집·사무실 PC를 개인 추론 서버로)

**어댑터 구성 (`LlmProvider` 구현 3종)**

| 구현 | 대상 | 구조화 출력 방법 |
| --- | --- | --- |
| `CloudProvider` | 파싱 프록시 → Claude / OpenAI / Gemini | 각 공급자의 네이티브 JSON 스키마·tool use |
| `OpenAiCompatProvider` | LM Studio, vLLM, llama.cpp server, 기타 호환 서버 | `response_format: json_schema` — LM Studio는 OpenAI와 동일 형식의 스키마 강제를 지원하며, 7B 미만 모델은 구조화 출력이 불안정할 수 있다고 명시한다 ([LM Studio 문서](https://lmstudio.ai/docs/developer/openai-compat/structured-output)) |
| `OllamaProvider` | Ollama | Ollama의 OpenAI 호환 엔드포인트는 `json_schema`를 무시하므로 ([llm-cli](https://github.com/nlink-jp/llm-cli)) 네이티브 `/api/chat`의 `format` 필드에 JSON 스키마를 전달 |

- 공통 폴백: 스키마 강제가 안 되는 서버는 프롬프트에 스키마를 넣어 요청하고, 응답을 JSON 파서 + 스키마 검증기로 검사 → 실패 시 "JSON만 다시 출력" 1회 재시도 → 그래도 실패면 규칙 기반 폴백
- 로컬 모델은 상대 날짜 산술이 약하므로 5.3의 후처리 규칙 비중을 높이고, 프롬프트에는 "오늘은 2026-10-20 화요일"처럼 요일까지 명시한다
- 타임아웃: 로컬은 30초(기본), 초과 시 클라우드 폴백 여부를 사용자가 설정

**지원 범위**

- v1.0: 데스크톱(macOS·Windows)에서 Ollama·LM Studio·OpenAI 호환 서버 연결, 모바일은 원격 주소 연결만
- v1.5: 앱 내장 로컬 모델 (iOS Foundation Models, Android Gemini Nano / LiteRT-LM, 데스크톱 llama.cpp 내장) — 설치형 서버가 없는 일반 사용자용

## 6. 플랫폼별 UX

핵심 화면(검토 카드)은 4개 플랫폼에서 동일하게 두고, 앱에 진입하는 방식만 플랫폼 관습에 맞춘다.

| 항목 | macOS | Windows | iOS | Android |
| --- | --- | --- | --- | --- |
| 주 진입점 | 메뉴바 아이콘 + `⌘C` 더블 탭 | 트레이 아이콘 + `Ctrl+C` 더블 탭 | 공유 시트 (Share Extension) | 공유 인텐트 (ACTION\_SEND) |
| 보조 진입점 | Services 메뉴, 사용자 지정 단축키, 클립보드 감지 | 컨텍스트 메뉴, 사용자 지정 단축키, 클립보드 감지 | 클립보드 감지(앱 열 때), 홈 화면 위젯, 단축어(Shortcuts) | 클립보드 감지(앱 열 때), 홈 위젯, 빠른 설정 타일 |
| 표시 형태 | 작은 플로팅 패널 (포커스 잃으면 닫힘) | 플로팅 패널 | 공유 확장 안의 바텀 시트 (본 앱 미호출) | 바텀 시트 |
| 캘린더 기본값 | Apple Calendar (EventKit) | Google Calendar | Apple Calendar | Google Calendar |
| 로그인 | Google OAuth (시스템 브라우저) | Google OAuth | Google OAuth (ASWebAuthenticationSession) | Google OAuth (Credential Manager) |
| 클립보드 접근 | 자유 | 자유 | 앱 활성화 시, iOS 16+ 붙여넣기 권한 안내 | Android 10+ 앱 활성화 시만 |
| 알림 | 등록 완료 시스템 알림 | 토스트 알림 | 로컬 알림 (이벤트 알림은 캘린더가 담당) | 로컬 알림 |

**플랫폼별 주의점**

- iOS 공유 확장은 본 앱을 깨우지 않는다. iOS는 확장에서 `openURL`로 메인 앱을 강제 실행하는 것을 막고 있어 App Group + URL scheme 우회는 업데이트마다 막히거나 심사 반려 사유가 된다. 확장 자체가 가벼운 SwiftUI 검토 카드 1장을 띄우고, 안에서 프록시를 호출해 EventKit(또는 Google API)으로 등록한 뒤 닫힌다 — 메모리 한도(약 120MB)와 "3초" UX를 둘 다 만족한다. Flutter 엔진은 확장에 싣지 않는다
- 확장이 본 앱과 같은 파싱·후처리·캘린더 로직을 쓰도록 Rust 코어를 XCFramework로 빌드해 공유한다 (8.1.1). Google 토큰은 App Group 키체인으로 공유하고, EventKit 권한은 온보딩에서 본 앱이 미리 받아 둔다
- Android 공유 인텐트로 받은 텍스트는 `EXTRA_TEXT`로 들어오며, 카카오톡은 선택 텍스트 공유를 지원하므로 그 경로를 온보딩에서 안내한다
- macOS 메뉴바 앱은 Dock 아이콘 없이 상주(LSUIElement), 설정 창만 일반 창으로 띄운다
- Windows는 시작 시 자동 실행 옵션과 트레이 최소화를 기본 제공한다
- 데스크톱에서 클립보드 폴링은 하지 않는다 (배터리·프라이버시). 더블 탭·단축키·아이콘 클릭 시점에만 읽는다. 선택 영역을 자동으로 읽는 Accessibility 권한은 요청하지 않는다

## 7. 캘린더 연동

캘린더 쓰기는 공통 인터페이스 `CalendarProvider` 뒤에 두고, 플랫폼별 구현 2종(Google, Apple)을 둔다.

```
interface CalendarProvider {
  listCalendars(): Calendar[]
  findConflicts(start, end): Event[]
  findDuplicate(title, start): Event | null
  createEvent(event): EventId
  updateEvent(id, event): void
  deleteEvent(id): void   // 실행 취소용
}
```

| 항목 | Google Calendar | Apple Calendar |
| --- | --- | --- |
| 접근 방식 | Google Calendar API v3 (REST), OAuth 2.0 | EventKit (iOS/macOS 네이티브 프레임워크) |
| 지원 플랫폼 | 4개 전체 | iOS, macOS만 (Windows/Android는 선택지에서 숨김) |
| 필요 권한 | `calendar.events` 스코프 (전체 읽기 아님, 이벤트 범위만) | `NSCalendarsWriteOnlyAccessUsageDescription` (iOS 17+ 쓰기 전용) — 중복·충돌 감지가 필요하면 전체 접근 요청 |
| 토큰 저장 | 리프레시 토큰을 OS 키체인/Keystore/DPAPI에 저장 | 권한만 있으면 됨 |
| 다중 계정 | 지원 (계정별 캘린더 목록) | 시스템에 등록된 모든 계정 캘린더 자동 노출 |
| 중복 감지 | `events.list`로 ±15분 범위 조회 후 제목 유사도 비교 | `predicateForEvents(withStart:end:calendars:)` |
| 오프라인 | 로컬 큐에 저장 후 온라인 시 재시도 | 즉시 반영(iCloud 동기화는 OS 담당) |
| 할당량 | 사용자당 하루 수십 건 수준으로 무시 가능, 프로젝트 기본 한도 내 | 없음 |
| 심사 요건 | OAuth 앱 검증 (민감 스코프, 데모 영상 제출) | 앱스토어 권한 설명 문구 심사 |

**권한 모델 원칙**

- 최소 스코프: Google은 `calendar.events`만, Apple은 iOS 17+에서 가능하면 쓰기 전용 권한 — 중복 감지 기능은 "전체 접근 허용 시에만" 활성
- 온보딩에서 캘린더 연결을 건너뛸 수 있고, 첫 등록 시점에 다시 요청. iOS에서는 EventKit 권한을 본 앱 온보딩에서 미리 받아 공유 확장 안에서 권한 프롬프트가 뜨지 않게 한다
- iOS 공유 확장과 본 앱은 Google 토큰을 App Group 키체인으로 공유한다 (6절)
- 토큰 폐기: 설정 > 계정에서 연결 해제 시 로컬 토큰 삭제 + Google 토큰 revoke 호출
- 아이폰 + 회사 윈도우 PC 조합 사용자는 Windows에서 Apple Calendar에 쓸 수 없다. v1.0 온보딩에서 이 조합을 감지하면 "아이폰 기본 캘린더 앱에 Google 계정을 추가하면 양쪽에서 같은 캘린더를 쓸 수 있다"는 안내를 보여 준다 — 핵심 가치 "어떤 플랫폼에서든 같은 캘린더"를 지키는 현실적인 경로

**v1.5 후보:** Outlook (Microsoft Graph), iCloud 캘린더 CalDAV (앱 암호 방식 — Windows·Android에서 Apple 캘린더 쓰기), Naver 캘린더 (공개 API 없음 → CalDAV 또는 제외), CalDAV 일반 지원

## 8. 기술 아키텍처

**권장 스택: Flutter UI + Rust 코어(`flutter_rust_bridge`) + 얇은 네이티브 진입점 + 파싱 프록시 + 계정·동기화 백엔드.** 파싱 후처리·RRULE·중복 검사·Provider 어댑터는 Rust 크레이트 하나에 두고, Flutter 본 앱은 `flutter_rust_bridge`로, iOS 공유 확장(SwiftUI)은 XCFramework로 같은 크레이트를 쓴다. 4개 플랫폼 UI·로직 공유율 85% 이상, 네이티브는 공유 시트·전역 단축키·EventKit 3곳만 직접 작성한다.

### 8.1 크로스플랫폼 프레임워크 비교

| 후보 | 4플랫폼 커버 | 데스크톱 메뉴바/트레이 | 공유 시트·인텐트 | EventKit 접근 | 평가 |
| --- | --- | --- | --- | --- | --- |

| 전부 네이티브 (SwiftUI + Kotlin + WinUI) | 최고 품질 | 각각 최적 | 각각 최적 | 직접 | 팀 3\~4개 필요, 동시 출시 불가 |

#### 8.1.1 Tauri 2를 1순위로 두지 않은 이유

**결론: 데스크톱만이라면 Tauri가 더 좋은 선택이고, 4플랫폼 동시 출시에서는 모바일 쪽 리스크 때문에 Flutter를 1순위로 뒀다.** 다만 JS가 Rust에 익숙하고 Claude Code가 구현을 맡는 조건이라면 격차는 좁아지므로, 0단계에서 2\~3일짜리 PoC로 확정하는 것을 제안한다.

**현황 (2026-10 기준)**

- Tauri 2.0은 2024년 10월 안정화되며 iOS·Android 지원을 추가했고, 2026년 중반 현재 2.11 라인이다 ([mayhemcode](https://www.mayhemcode.com/2026/07/build-mobile-and-desktop-apps-from-one.html))
- Spacedrive, AppFlowy 등 데스크톱 프로덕션 사례는 충분하다. 반면 Tauri 팀 스스로 RC 시점에 "모바일이 1급 시민인 릴리스는 아니며, 데스크톱 기능·플러그인이 모두 모바일로 이식되지는 않았다"고 밝혔다 ([Tauri 2.0 RC 블로그](https://v2.tauri.app/es/blog/tauri-2-0-0-release-candidate/))

**이 앱에서 특히 걸리는 지점 4가지**

| 지점 | Tauri 2 | Flutter | 이 앱에 미치는 영향 |
| --- | --- | --- | --- |
| 렌더링 | 시스템 웹뷰 (WKWebView / WebView2 / Android WebView) — OS·버전별 폰트·줄바꿈·IME 차이 | 자체 렌더러(Impeller), 4플랫폼 동일 픽셀 | 검토 카드의 한국어 인라인 편집에서 웹뷰 IME 조합 이슈가 재현되기 쉬움 |
| 공유 시트 / 공유 인텐트 | 공식 플러그인 없음, Swift·Kotlin으로 직접 작성 | 커뮤니티 플러그인 + iOS 확장만 Swift | 주 진입점이 모바일 공유이므로 가장 먼저 부딪히는 부분 |

**Tauri가 이기는 지점**

- 데스크톱 바이너리 수 MB(Flutter는 30MB 안팎), 메모리 사용량 낮음 — 상주형 메뉴바·트레이 앱에 유리
- tray, global-shortcut, autostart, clipboard가 공식 플러그인 — 데스크톱 진입점은 Flutter보다 안정적
- 파싱 후처리(날짜 산술, RRULE, 중복 검사)와 Provider 어댑터를 Rust로 작성하면 타입 안전성과 테스트 용이성이 높다
- JS의 기존 Rust 경험(MediaOrganizer)을 그대로 활용

**권장안: Rust 코어 + Flutter UI.** 파싱 후처리·어댑터·로컬 히스토리를 Rust 크레이트로 만들고 `flutter_rust_bridge`로 연결하면, Tauri의 Rust 장점은 가져가면서 모바일 UI·플러그인 리스크는 Flutter 쪽에 둔다. 같은 크레이트를 XCFramework로 빌드하면 iOS 공유 확장(SwiftUI)도 본 앱과 100% 동일한 파싱·후처리·캘린더 로직을 쓴다 — 확장을 네이티브로 만들 때 생기는 로직 중복을 막는 유일한 방법이다. 크레이트는 나중에 Tauri나 CLI로도 재사용 가능하다.

**결정 기준 (0단계 PoC, 2\~3일)**

1. 두 스택으로 "iOS 공유 시트 → 카드 표시 → EventKit 등록" 경로만 구현
2. 한국어 입력 편집(IME), 카드 렌더 일관성, 빌드 파이프라인 길이를 비교
3. 데스크톱이 주력이고 모바일을 후순위로 미룰 수 있다면 Tauri, 4개 동시가 조건이면 Flutter(+Rust 코어)

### 8.2 시스템 구성

- **Rust 코어 (크레이트 `c2c-core`):** 추출 스키마 타입, 상대 날짜 확정·시간대·공휴일 후처리, RRULE 생성, 중복·충돌 판정, `LlmProvider`·`CalendarProvider` 어댑터, 로컬 히스토리(SQLite). Flutter에는 `flutter_rust_bridge`, iOS 확장에는 XCFramework로 제공
- **클라이언트 (Flutter):** UI, 검토 카드, 온보딩, 설정, 계정. 상태 관리는 Riverpod, 모델 직렬화는 freezed.
- **네이티브 진입점:** iOS Share Extension(SwiftUI 카드 1장 + Rust 코어, 본 앱 미호출), Android Share Activity(Kotlin), macOS 메뉴바·Services·복사 더블 탭(Swift), Windows 트레이·복사 더블 탭(C++ 또는 기존 플러그인), EventKit 브리지(Swift, iOS/macOS 공유).
- **파싱 프록시 (서버리스 함수 1개):** LLM API 키를 클라이언트에 넣지 않기 위한 얇은 중계. 요청 서명 검증, 레이트 리밋, 모델 라우팅(공급자 교체), 평가 로그(옵트인 시만). 본문은 디스크에 쓰지 않는다. Cloudflare Workers 또는 AWS Lambda.
- **계정·동기화 백엔드 (프록시와 분리):** 로그인(Apple·Google·매직 링크), 기기 목록·대수 제한, 구독 엔타이틀먼트, 설정·사용자 사전 동기화, 옵트인 히스토리 동기화. Supabase(Auth + Postgres RLS) + RevenueCat 조합으로 1인 운영에 맞게 구축. 원문은 사용자가 동기화를 켠 경우에만 컬럼 암호화(AES-GCM)로 저장.
- **Google Calendar API:** 클라이언트에서 직접 호출 (OAuth 토큰은 기기에만 존재, 서버 경유 없음).
- **온디바이스 모드:** 프록시 없이 로컬 모델 호출, 네트워크 요청 0건 (동기화를 끄면 계정 백엔드 호출도 없음).

메시지 본문은 프록시를 거쳐 LLM으로만 가고, 캘린더 토큰과 히스토리는 기기 밖으로 나가지 않는다.

### 8.3 데이터 흐름 (클라우드 모드 기준)

1. 입력 텍스트 + 컨텍스트(현재 일시, 시간대, 기본값) → 프록시 (TLS, 익명 기기 토큰으로 서명)
2. 프록시 → LLM API (구조화 출력 요청) → JSON 응답
3. 클라이언트 후처리: 상대 날짜 확정, 시간대 부착, 신뢰도 임계값 적용, 중복·충돌 조회
4. 검토 카드 표시 → 사용자 확인
5. `CalendarProvider.createEvent` → Google API 또는 EventKit
6. 로컬 히스토리 저장 (원문·결과), 서버에는 저장하지 않음

### 8.4 저장소·배포

- 모노레포 1개: `core/`(Rust 크레이트), `app/`(Flutter), `ios/`·`android/`·`macos/`·`windows/`(플랫폼 코드, iOS 공유 확장 포함), `proxy/`(파싱 프록시), `backend/`(Supabase 마이그레이션·RLS 정책), `eval/`(파싱 평가셋·스크립트)
- CI: GitHub Actions — Rust 테스트·4플랫폼 빌드·XCFramework 빌드, 파싱 회귀 테스트, 스토어 배포(Fastlane, MSIX, DMG notarization)
- 배포 채널: App Store(iOS·macOS), Google Play, Microsoft Store + 직접 다운로드(Windows)

## 9. 프라이버시와 보안

붙여 넣는 텍스트는 사적인 대화다. 원칙은 "서버는 기억하지 않는다, 기기는 사용자 것이다".

**메시지 내용 처리 원칙**

- 파싱 프록시는 요청을 LLM에 전달만 하고 디스크에 쓰지 않는다 (로그에도 본문 제외, 길이·지연시간·결과 코드만 기록)
- LLM 공급자는 학습 비사용(zero data retention) 약관이 있는 API 플랜만 사용
- 평가셋 수집은 명시적 옵트인 + 건별 "이 예시 보내기" 버튼으로만, 기본 꺼짐
- 히스토리는 기본적으로 기기 로컬 SQLite에만 저장되고 서버로 가지 않는다. 사용자가 "기기 간 히스토리 동기화"를 켠 경우에만 계정 백엔드에 컬럼 암호화(AES-GCM, 키는 서버 KMS)로 저장. 종단간 암호화는 v1.5 옵션(기기 간 QR 키 교환)으로 두고, v1.0에서는 약속하지 않는다
- 앱 삭제 시 로컬 히스토리 삭제, 설정에서 로컬·서버 히스토리 전체 삭제 가능
- 전화번호·계좌번호 패턴은 전송 전 클라이언트에서 마스킹 (옵션, 기본 켜짐)

**온디바이스 옵션**

- 설정에서 "기기에서만 분석" 선택 시 네트워크 요청 0건, 앱 심사 시 프라이버시 라벨에 반영
- 지원 기기: Apple Intelligence 지원 기기(Foundation Models), Gemini Nano 지원 안드로이드, 데스크톱은 3B급 로컬 모델 다운로드(약 2GB) 선택

**인증·토큰**

- Google 리프레시 토큰: iOS/macOS Keychain, Android Keystore(EncryptedSharedPreferences), Windows DPAPI
- 프록시 호출 인증: 기기별 익명 키 쌍, App Attest / Play Integrity로 정품 앱 검증 (v1.0은 레이트 리밋만, v1.5에서 Attest)
- LLM API 키는 서버에만 존재

**규정·심사**

- 개인정보처리방침에 "입력 텍스트는 분석 목적으로 제3자 LLM 공급자에 전송되며 저장되지 않음" 명시
- Google OAuth 민감 스코프 검증 (제한 스코프 아님 → CASA 감사 불필요), 데모 영상 준비
- 앱스토어 프라이버시 영양표: 데이터 수집 "없음" 또는 "진단 데이터만"

### 10.1 종합 가격 체계 (멀티플랫폼·멀티 LLM 기준)

가격을 가르는 축은 두 가지다: **기기·사람 수**(개인 → 가족 → 팀)와 **AI 비용 부담 주체**(우리 클라우드 → 사용자 키/로컬). 로컬 LLM이나 자기 API 키를 쓰는 사용자는 AI 비용을 우리가 지지 않으므로 더 싸게 받는다.

**가격 설계 메모**

- 무료 플랜의 첫 14일 100건은 콜드 스타트 대책이다. 타깃 사용자는 월 30건을 일주일에 다 쓰므로, 습관이 붙기 전에 결제 벽을 만나면 삭제한다. 트라이얼은 기기당 1회, 계정 로그인 시 1회로 묶어 남용을 막는다
- 프로의 "월 1,000건 공정 사용"은 5.7 기준 월 200\~300원 원가라 사실상 무제한이지만, 봇·남용 방어용 상한으로 둔다. 초과 시 차단이 아니라 가성비 모델로 자동 전환
- 라이트는 "내 모델을 쓰는데 왜 돈을 내나"에 대한 답이 필요하다 → 라이트의 가치는 AI가 아니라 동기화 서버(지속 비용)이므로 월 구독으로 두되, 베타에서 "BYOK 언락 일회성 구매(동기화 제외) vs 라이트 월 구독(동기화 포함)"을 A/B로 검증한다. 무료 사용자에게도 BYOK·로컬은 열어 두고 동기화만 막는다
- 연간 요금은 월 요금의 약 7.5개월치, 평생은 연간 2년치 — 출시 후 3개월만 판매
- 결제: iOS·Android는 스토어 인앱 결제(수수료 15\~30%), 데스크톱·웹은 Paddle 또는 토스페이먼츠(수수료 5% 안팎). 어디서 결제해도 계정 엔타이틀먼트는 하나 — RevenueCat으로 통합 (8.2)

### 10.2 회원 관리·지원 서비스

**계정**

- 로그인: Apple·Google 계정 + 이메일 매직 링크. 비밀번호는 두지 않는다 (Supabase Auth)
- 익명 사용: 로그인 없이 무료 플랜 사용 가능(기기 로컬), 로그인 시 기기 데이터를 계정에 병합
- 기기 관리: 설정 > 기기에서 연결된 기기 목록·이름·마지막 사용일 확인, 원격 로그아웃
- 동기화 대상: 설정, 기본값, 캘린더 매핑, 사용자 사전(장소·사람 별칭)은 기본 동기화. 히스토리(원문 포함)는 **옵트인** — 켜면 서버에 컬럼 암호화로 저장, 끄면 서버에서 삭제 (9절)
- 데이터 권리: 설정에서 내 데이터 내보내기(JSON), 계정·데이터 완전 삭제 (처리 즉시, 백업 30일 내 소거)

**구독·결제**

- 플랜 변경은 즉시, 다운그레이드는 기간 말 적용, 환불은 스토어 정책 준수 + 데스크톱 결제는 14일 무조건 환불

- 팀: 관리자 콘솔(멤버 초대·제거, 좌석 수, 조직 BYOK 키, 월별 사용량 CSV), SSO는 Google Workspace부터

# 0003. 이벤트 조립과 평가 채점

- 상태: 채택 (2026-10-27)
- 관련: PRD 2절(성공 지표)·4.2·4.3·5.1·5.4, ADR 0001 미결 4·5번, ADR 0002
- 코드: `core/src/assemble.rs`, `core/tests/assemble.rs`, `eval/src/score.rs`, `eval/src/main.rs`

## 배경

해석기(ADR 0002)는 필드 하나를 날짜·시각으로 확정한다. 검토 카드에 올리려면 이벤트 단위로 묶어야 한다. 종료 기본값, 종일 여부, 시간대, 복수 후보 표시를 붙이고, 모델이 낸 모호성 플래그와 후처리 플래그도 합쳐야 한다. 평가셋 정확도를 재려면 이 결과를 `expected`와 비교하는 채점기도 필요하다.

## 결정

### 1. 인터페이스

`assemble(&ExtractionResult, &ParseContext, &HolidayTable) -> Vec<Result<EventDraft, AssembleError>>`

- `no_event_found`이면 빈 목록을 돌려준다. 카드에서 "일정을 찾지 못했어요"를 띄운다 (PRD 5.4)
- 결과는 이벤트마다 따로 낸다. 한 건이 해석에 실패해도(예: 없는 공휴일) 나머지 카드는 보여 줄 수 있다
- `EventDraft`는 캘린더에 쓰지 않는 초안이다
  - 제목은 `Option`이다. 없으면 카드에서 입력받는다
  - 등록은 사용자가 카드에서 확인한 뒤 `CalendarProvider`로 한다 (CLAUDE.md 규칙 1)

### 2. 조립 규칙

| 항목 | 규칙 | 근거 |
| --- | --- | --- |
| 종일 | 모델이 `all_day: true`를 냈거나 시작에 시각 표현이 없으면 종일 | "내일 회의"처럼 시각이 없는 메시지 |
| 종일 종료일 | 종료일(포함). 없거나 시작보다 앞서면 시작일 | `EventTime::AllDay` (ADR 0001 5절) |
| 종료 없음 | 시작 + `TimeDefaults.duration_minutes`(기본 60분) | PRD 4.2 "+1시간" |
| 자정을 넘는 종료 | "밤 11시~1시"는 해석기가 다음 날로 넘긴다. explicit으로 같은 날짜에 적힌 "23:00~01:00"은 다음 날로 넘겨 12시간 이내가 될 때만 넘긴다 | 모델이 날짜를 잘못 적었을 가능성 대비 |
| 그 밖에 시작 이후가 아닌 종료, 시각 없는 종료 | 기본 길이로 두고 `duration_unknown` 플래그. 모델이 낸 종료 값은 대안으로 남긴다 | PRD 4.2 "기간 불명" |
| 시간대 | `ParseContext.time_zone`(IANA)를 `chrono-tz`로 해석해 `DateTime<FixedOffset>`로 만든다 | ADR 0001 미결 5번 → `chrono-tz` 채택 |
| 서머타임으로 두 번 있는 로컬 시각 | 이른 쪽 | 일정을 놓치기보다 앞서 알린다 (ADR 0001 8절과 같은 원칙) |
| 서머타임으로 없는 로컬 시각 | 해당 이벤트만 오류 `NonexistentLocalTime` | 한국 시간대에서는 생기지 않는다 |
| 모호성 플래그 | 모델 플래그 + 해석기 플래그를 합친다. `year_missing`·`multiple_candidates`·`explicit_relative_mismatch`는 모델이 내도 버린다 | 이 셋은 코드가 판단한다 (ADR 0001 7절) |
| 복수 후보 | 같은 `candidate_group`에 두 건 이상이면 각 이벤트에 `multiple_candidates` 플래그를 붙이고, 다른 후보의 시작을 대안으로 넣는다. 한 건뿐인 그룹에는 붙이지 않는다 | PRD 5.4 3번 |

`duration_unknown`은 종료가 아예 없을 때는 자동으로 붙이지 않는다. 대부분의 메시지에 종료가 없어서, 붙이면 거의 모든 카드가 하이라이트되기 때문이다. 모델이 판단해 낸 경우만 남긴다.

### 3. 평가 실행기

- 실행 형식: `eval --set <케이스.jsonl> --outputs <모델출력.jsonl> [--min-accuracy 0~1]`
  - 출력 파일은 케이스와 같은 줄 순서로 모델 출력(PRD 5.1 JSON)을 담는다
  - 출력을 `assemble`로 조립해 `expected`와 비교한다
  - 정확도가 `--min-accuracy`보다 낮으면 실패로 끝난다 (CLAUDE.md 규칙 7)
- 공급자를 붙이는 `--provider`는 0-6 이후에 쓴다
  - 그 전에는 모델 출력을 기록해 두고 `--outputs`로 돌린다
  - 이렇게 하면 후처리(해석기·조립)만 바뀐 변경도 회귀를 잡을 수 있다
- CI는 PRD 3절 예시 3건(`eval/fixtures/prd-examples*.jsonl`)을 정확도 100%로 돌린다
  - 출력 fixture는 PRD 5.1 형식에 맞춰 사람이 쓴 것이고, 실제 모델 출력이 아니다
- 평가 컨텍스트
  - 기준일: 케이스의 `reference_date` 00:00. 해석기는 날짜만 쓴다
  - 시간대: `Asia/Seoul`
  - 나머지 설정은 기본값

### 4. 채점 규칙 (잠정)

ADR 0001 미결 4번(평가 채점)에 대한 잠정안이다.

- 케이스 단위로 정답/오답을 매긴다. 아래가 모두 맞아야 정답이다
  - 일정 수
  - 일정별 시작
  - 종료 (`expected`에 있을 때만)
  - 종일 여부
  - 후보 묶음
- 후보 묶음은 번호가 아니라 어느 일정끼리 같은 묶음인지로 비교한다
- 일정 순서는 `expected`와 같아야 한다
- 제목·장소는 아직 채점하지 않는다. 문자열 일치 기준(공백, "2번출구"와 "2번 출구")을 정해야 한다
- PRD 2절 지표가 "파싱 정확도 (날짜·시간)"이므로 날짜·시간만으로 시작한다

## 대안

- 종료가 없으면 항상 `duration_unknown`: 카드 대부분이 하이라이트되어 기각
- 조립 실패 시 전체 결과를 오류로: 일정 여러 개 중 하나만 틀려도 카드를 하나도 못 보여 줘서 기각
- 시간대 라이브러리 `jiff`: 이미 `chrono`를 쓰고 있어서 같은 생태계의 `chrono-tz`를 택했다

## 미결

1. **제목·장소 채점.** 문자열 비교 기준을 정해야 한다
2. **일정 순서.** 순서가 달라도 정답으로 볼지 정해야 한다. 지금은 순서까지 맞아야 정답이다
3. **실제 모델 출력 기록.** 0-6 어댑터가 생기면 `--provider`로 바로 채점할지, 출력을 기록해 `--outputs`로 고정할지 정해야 한다

## 결과

- 조립 테스트 9건(`core/tests/assemble.rs`)과 채점 테스트 6건(`eval/tests/score.rs`)
- CI가 PRD 예시 3건의 모델 출력 → 조립 → 채점을 정확도 100%로 확인한다
- 해석기 보완: 날짜 없는 종료 시각이 그날 안에 시작 이후로 맞출 수 없으면 다음 날로 넘긴다 ("밤 11시~1시" → 다음 날 01:00)
